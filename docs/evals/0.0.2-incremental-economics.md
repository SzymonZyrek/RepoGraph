# 0.0.2 incremental economics evidence

Issue: #12  
Evidence PR: #39  
Reference CI run: 32 on Ubuntu 24.04 / Node 22.23.3

This evaluation exists to answer one question: does the 0.0.2 path avoid doing full-rebuild work for the normal high-velocity case of small commits?

It is not a general performance SLA and it is not intended to make broad changes look artificially good.

## Fixture

The reproducible harness in `scripts/eval-incremental.mjs` creates:

- 240 TypeScript source files;
- 24 bounded dependency clusters of 10 files each;
- 8 sequential one-file edits;
- one rename-only commit;
- one dependency-affecting edit;
- one broad mechanical change touching all 240 source paths;
- one branch/merge scenario.

For every scenario it records warm incremental work and a cold full rebuild of the same target revision.

## Observed evidence

### Normal tiny commits

Across the eight one-file edits:

- median incremental wall time: **57.56 ms**;
- median full rebuild wall time: **734.44 ms**;
- median incremental/full ratio: **0.08**;
- reparsed files: **1 of 240 (0.42%)** per edit;
- reused syntax artifacts: **239 of 240** per edit;
- touched graph nodes: **1**;
- invalidated graph nodes: **1**;
- touched graph edges: **2**;
- cache growth: about **497 bytes** per unique changed syntax artifact.

The measured expensive work therefore follows the changed surface rather than rebuilding all 240 source artifacts.

### Rename-only

The rename-only commit measured:

- incremental: **50.97 ms**;
- full rebuild: **743.62 ms**;
- reparsed files: **0**;
- reused syntax artifacts: **240**;
- cache growth: **0 bytes**;
- touched/invalidated graph nodes: **2 / 2**.

This is the intended content-addressed behavior: path identity changes while unchanged blob content is reused.

### Dependency-affecting edit

The one-file dependency edit measured:

- incremental: **63.86 ms**;
- full rebuild: **739.16 ms**;
- reparsed files: **1**;
- touched nodes: **1**;
- touched edges: **3**;
- invalidated nodes: **1**.

Dependency-edge work expands only when the dependency surface changes.

### Branch / merge

The merge-base scenario measured:

- incremental: **57.67 ms**;
- full rebuild: **752.59 ms**;
- reparsed files: **1**;
- touched/invalidated nodes: **1 / 1**.

The merge path therefore retains the same narrow steady-state behavior for this fixture.

### Broad mechanical change

The deliberately broad change touched all 240 source paths and measured:

- incremental: **1626.18 ms**;
- full rebuild: **754.64 ms**;
- incremental/full ratio: **2.15**;
- touched/invalidated graph nodes: **240 / 240**;
- touched edges: **456**;
- syntax artifacts reparsed: **41** and reused: **199**.

Only 41 new syntax artifacts were needed because content-addressing also reuses identical blobs across different paths, but once the graph change surface itself is broad the incremental planning path is more expensive than a clean rebuild.

That crossover is useful evidence, not a failure to hide. 0.0.2 optimizes the normal small-commit path; a future consumer-driven optimization may choose a full rebuild automatically when the changed surface is sufficiently broad.

## Evidence-derived checkpoint

For this fixture, 0.0.2 has earned the following engineering checkpoint:

- a normal one-file commit reparses only the changed content artifact;
- a rename with identical content reparses nothing;
- normal small commits touch/invalidates a narrow graph slice rather than the whole graph;
- median incremental time for the tiny-edit sequence is materially below a cold full rebuild;
- broad changes are allowed to cross over into full-rebuild territory and must remain visible in metrics.

These are evidence-derived expectations for regression testing, not universal latency promises.

## Reproduce

```bash
npm run eval:incremental
```

The command builds RepoGraph, creates the synthetic Git history in a temporary directory, executes all scenarios and emits the raw JSON evidence to stdout.
