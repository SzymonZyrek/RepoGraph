# 0.0.3 consumer compatibility proof

This fixture proves that the current generic RepoGraph contract is sufficient for the two first consumers without adding VibeGuard- or Hacka-specific rules to core.

The executable proof lives in `test/consumer-compatibility.test.ts`.

## VibeGuard-shaped scenario

The fixture builds repository evidence from the normal Git, TS/JS and repository-relationship extractors, then applies a consumer-owned authoritative overlay for two capabilities and two owners.

Starting from a changed Payments source file, a bounded reverse traversal recovers:

- the Payments capability;
- its authoritative Owner;
- the directly related Payments test;
- causal evidence that keeps derived repository facts distinct from explicit overlay authority.

The same traversal does not pull in the unrelated Analytics capability, Owner or tests. This is the review-evidence invalidation boundary needed by VibeGuard: RepoGraph returns the affected evidence slice, while VibeGuard remains responsible for the review decision.

## Hacka-shaped scenario

The Hacka fixture queries the same repository graph without any VibeGuard overlay.

A bounded bidirectional traversal from the same Payments source file recovers:

- the implementation source;
- the related test;
- the package entrypoint;
- the declared type contract.

No capability, Owner or review-policy node is required. The consumer chooses its own traversal budget and edge kinds.

## Cross-product evidence handoff

Two independent graph builds for the same repository/ref are graph-equal and expose the same stable node identities and provenance.

The fixture then simulates a durable `hacka.work-request/v1` payload carrying:

- repository identity;
- exact base SHA;
- a RepoGraph evidence node ID.

A fresh graph build at that pinned SHA resolves the same evidence node and confirms provenance against the requested repository/commit.

This is the intended boundary for the VibeGuard → GitHub work request → Hacka loop: GitHub carries durable workflow state, while RepoGraph only derives pinned repository facts.

## What this deliberately does not add

- no RepoGraph GitHub write credential;
- no webhook receiver;
- no task queue;
- no hidden mutable workflow state;
- no capability/Owner/review semantics in RepoGraph core;
- no Hacka scheduler semantics in RepoGraph core.

The proof uses the same public graph, overlay, provenance and traversal contracts already shipped in 0.0.3 slices #13–#15.
